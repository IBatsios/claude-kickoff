## Findings, in order of severity

1. **No default branch exists after the build.** `SKILL.md` step 5 says `git init`, then the `feature/initial-scaffold` branch, then one commit. Checking out the new branch before the first commit leaves `main` unborn, so the repository has one branch. Runbook step 0.6 (from "The push" in `reference/hosts.md`) then says to push that branch and open a pull request to the default branch; on an empty GitHub repository the pushed branch becomes the default, and there is nothing to open the pull request against. Fix, either: `git branch main` at the scaffold commit and push `main` before the feature branch in 0.6; or put the scaffold commit on `main` and let Task 01 be the first branch. The second reads better with `protect_default_branch`, since the scaffold is documents only. Files: `SKILL.md` step 5, `reference/hosts.md`, `templates/expected-files.md`.
2. **The skills list is too long to show.** `SKILL.md` section 6 says to show the detected list once and let the user trim it. Detection found about 190 entries, most for other stacks (Go, Rust, Kotlin, Django, Laravel, Ansible, homelab, 3D). Showing them all is unusable. The run showed the twenty or so that fit the stack, grouped, and named the remaining families in one line. Fix: section 6 says to show only the skills whose description fits the stack or the project type, with a count of the rest, and that the user may add any of the rest by name. Since the stack is what makes the filter possible, the list belongs at Section 8 of the walkthrough, not before Section 1.
3. **Two contradictions no check catches.** First: 6.5 was answered "admin can view results and progress per student" after 3.2 had said "one role, all are students". Second: `deployment.environments` came back as `[development]` alone with `deployment.target` Railway. `reference/checks.md` fires on the reverse cases only (roles without auth; local only with production). The run amended both and said so, which is the right outcome but the wrong mechanism. Fix: two rows in the contradictions table: "6.5 is yes, but 3.2 names no admin role: ask which is right, then add the role"; "Deployment target is not local only, but environments lack production: ask, then add it". Also the same rows in `docs/question-bank.md`.
4. **"Fine" on an optional section with nothing to accept.** Section 11 was answered "fine" when the run had offered no proposals. Blank would have recorded seven skipped questions; "I don't know" would have recorded seven unknowns; neither was what the user meant. The run proposed a value for each from the earlier sections and wrote them as the answers, saying so. `SKILL.md` section 2 does not say whether that is allowed. Decide: either optional sections carry a proposed answer drawn from earlier sections so that one word accepts them, or "fine" is answered with "blank or I don't know?". The first made Sections 12 to 14 the fastest of the walkthrough.
5. **The Railway and Fly.io deploy block has no domain step.** `templates/tasks/ts-prisma-postgres/deploy.md` renders "Reachable at {{url}}" with the intake's domain as an acceptance criterion, but the Railway/Fly.io steps never attach the domain; the Docker block does. The run added a step: add the custom domain on the service and create the DNS record it shows. Fix: add that step to the Railway/Fly.io block, and to the Vercel block, when `deployment.domain` is set. Same check for `templates/tasks/generic/deploy.md`.
6. **`pnpm/action-setup@v4` needs `packageManager`.** `reference/ci.md` says to add `pnpm/action-setup@v4` for pnpm. The action reads the pnpm version from the `packageManager` field of `package.json` and fails without it; `create-next-app` does not always write the field. The run added a sentence to Task 01. Fix: the same sentence in `ci.md`.
7. **LICENSE cannot carry the generated header.** `SKILL.md` rule 1 says generated files say so in their first line. A license text with a comment on top is not a license text. `docker-compose.yml` took a YAML comment. Fix: name `LICENSE` as the one exception in `SKILL.md` and in `templates/expected-files.md`.
8. **Minor, in one place.**
   - A section with both menu and prose fields costs two exchanges: the structured prompt returns first, then the prose questions go out in chat. Fourteen sections became about twenty exchanges. Not fixable without dropping the structured prompt; note it in `SKILL.md` so nobody counts it as a defect.
   - `templates/tasks/generic/definition-of-done.md` has no "Suggested skills" section, while `SKILL.md` step 3 implies every task may carry one. Say the definition of done never does.
   - `templates/docs/DECISIONS.md` puts 8.11 in D1's "Why" column. 8.11 is must-use library notes, not a reason for the stack. Render 8.11 as its own row, "Must use: ...", and leave D1's reason as "chosen in intake".
   - `templates/docs/PRD.md` builds the Users table from 3.1 with roles from 3.2, and says nothing about a role in 3.2 that no line of 3.1 mentions. The run added an admin row from 6.5. Say to add a row per such role.
   - Prose answers carried typos ("httpa", "deplot", "usimg"). The near-miss rule covers menus only. The run corrected the obvious ones and said so in the same message. Say that in `SKILL.md`, or say to write prose exactly as typed.
   - `templates/docs/CLAUDE.md` is loaded by Claude Code as a nested instruction file whenever a file in `templates/docs/` is read, placeholders and builder comments included. Harmless in a build, odd for anyone editing the templates. A different file name for the template (`CLAUDE.template.md`) and one line in `SKILL.md` would end it.
